Why 12 Years Teaching Maths Made Me a Better Architect

Samuel Nii Amu Darko · 12 Jan 2026

I taught Mathematics and ICT for twelve years before software became most of my work. The two jobs have more in common than they appear to. In both, something that makes sense in my head has to make sense to someone else: a JHS 3 student preparing for the BECE, a client describing how their shop runs, or a developer reading my code a year from now.

Students notice hand-waving

Junior high school students are quick to notice when an explanation does not hold together. If quadratic functions or binary arithmetic are explained with terms the class has memorised rather than understood, students can repeat the words and still get the exam question wrong. The words were never connected to anything they already knew.

The fix is to start from something the class can already do and build up one step at a time: counting in twos before binary, the area of a rectangle before expanding brackets. Each step should be small enough for a student to check for themselves.

Software has the same failure. A system can be described in confident technical language and still not be understood by the people who have to run it or change it. When I cannot explain a design in plain steps, the design is usually not finished.

Names are half the explanation

In a lesson, a badly chosen word costs a few minutes. In a database, it costs years. A table called records with a type column and a JSON field called data can store anything, and that is the problem: nobody can tell from the schema what a record is or what it may contain. Every query has to rediscover the rules.

Splitting it into sales, stock_movements and payments gives each table one meaning. The database can then enforce the rules itself: a payment must belong to a sale, a stock movement must name a product, a quantity cannot be empty. The same applies to API endpoints and function names. If a name needs a comment to explain it, it is usually the wrong name.

Normalising is factorising

Writing 3x + 3y as 3(x + y) states the shared factor once. Normalising a database does the same with facts. A customer's phone number belongs in one row, not copied onto every order they have placed, so that changing it once changes it everywhere. Duplicated facts drift apart: one copy gets updated, the other does not, and the system now holds two answers to the same question.

Worked examples come first

A good maths lesson shows a fully worked example before asking the class to try one, and the marking scheme is written before the exam is marked, not after. Both habits carry straight into software.

Before writing a function, it helps to write down one input and the exact output it should produce. That example becomes the first test. API documentation works the same way: one real request and its response explain more than a page of field descriptions.

Check understanding, not agreement

Asking a class "Do you understand?" gets a room full of nods. Asking one student to explain the step back in their own words shows what has actually been understood. Clients are no different. A client who agrees with a proposal has not necessarily understood it. Asking them to walk through how a sale, a refund or an end-of-day count would happen in the new system finds the gaps before any code is written.

Teaching did not make me a programmer. It did make me wary of any explanation, schema or interface that only makes sense to the person who made it.
