Low-Bandwidth UX for the African Internet

Samuel Nii Amu Darko · 5 Aug 2025

Many people in Ghana use the web on a phone with prepaid mobile data. Every megabyte a page downloads comes out of a data bundle someone has paid for, and on a weak signal it also takes time. A page built for these conditions should be useful before everything has loaded, and should cost as little as possible to load at all.

Send less JavaScript

Large client-side JavaScript bundles cost twice: once to download, and again for the phone to parse and run them. On a low-cost Android phone the second cost can be larger than the first.

Next.js Server Components help here. A component rendered on the server sends HTML to the browser and no JavaScript of its own. Only components marked with "use client" are shipped to the browser. On a product page, the description, price and photos can all be server components, and only the quantity selector and the add-to-cart button need to run in the browser. The page arrives as readable HTML and becomes interactive only where interaction is needed.

Images are usually the largest cost

On most pages, images outweigh everything else combined. Three habits make the biggest difference:

  • Convert photographs and artwork to WebP or AVIF, and resize them to the largest size they will actually be shown at. On this portfolio, a 2.3 MB PNG portrait became a 126 KB WebP, and a 3.0 MB roll-up banner became 119 KB.
  • Give every image a width and height, so the layout does not jump when it loads.
  • Add loading="lazy" to images below the first screen, but not to the main image at the top, which should load as early as possible.

Load only the fonts you use

Each font weight is a separate file, and it is easy to request every weight a font offers and use three of them. This site used to load fourteen weights across two font families; it now loads the eight the design actually uses. For many sites, the system font stack is a reasonable choice and costs nothing to download.

Make the slow state useful

On a slow connection, people spend real time looking at a page that is still loading. That state deserves design attention:

  • Server-rendered HTML shows the actual content before scripts finish, which is more useful than a page of grey placeholder boxes.
  • Links and forms should work as plain HTML, so a visitor can still move around the site or send an enquiry if a script fails to load.
  • A loading indicator should cover only the part of the page that is waiting, not block the whole screen.

Cache what does not change

Files whose names include a content hash, such as the scripts and stylesheets Next.js builds, can be cached by the browser for a year. A returning visitor then downloads only what has changed. For an app people open every day, a service worker can go further and keep the application shell available offline.

Test on a slow connection

A fast laptop on office Wi-Fi hides all of these problems. Browser developer tools can throttle the network to mobile speeds, and the Network panel shows how many bytes each page transfers. The most useful test is still the simplest: open the site on an inexpensive Android phone using mobile data, and use it the way a customer would.
