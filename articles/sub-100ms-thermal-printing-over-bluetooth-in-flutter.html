Thermal receipt printing with Flutter and Bluetooth

Samuel Nii Amu Darko · 28 Nov 2025

Most receipt printers in shops use ESC/POS, a command language Epson introduced and most thermal printer makers now support in some form. A Flutter point-of-sale app can talk to these printers directly over Bluetooth. This note covers what to send, how to lay out a receipt, and how to get the bytes across a Bluetooth link without losing any.

Bytes instead of bitmaps

Many printing plugins draw the whole receipt as an image and send it to the printer as raster data. That handles any layout, but it makes every receipt large. A 58 mm printer is usually 384 dots wide, so each row of the image is 48 bytes, and a receipt a few hundred rows tall becomes tens of kilobytes. Over Bluetooth, that takes noticeable time.

Text mode is much smaller. Plain characters go across as one byte each, and formatting is a few control bytes placed in front of the text:

import 'dart:convert';

const esc = 0x1B;
const gs = 0x1D;

final receipt = <int>[
  esc, 0x40,             // ESC @    reset the printer
  esc, 0x61, 0x01,       // ESC a 1  centre
  esc, 0x45, 0x01,       // ESC E 1  bold on
  ...ascii.encode('SHOP NAME\n'),
  esc, 0x45, 0x00,       // ESC E 0  bold off
  esc, 0x61, 0x00,       // ESC a 0  align left
  ...ascii.encode('Bread x2               GHS 24.00\n'),
  ...ascii.encode('Milk x1                GHS 18.50\n'),
  0x0A, 0x0A, 0x0A,      // feed the paper past the tear bar
  gs, 0x56, 0x42, 0x00,  // GS V 66 0  partial cut, where supported
];

Keeping a logo as a small image and printing everything else as text gives most of the visual benefit of raster printing at a fraction of the size.

Lay out for the paper width

With the default font, a 58 mm printer fits 32 characters on a line and an 80 mm printer fits 48. Receipts look tidy when every line is built to that width: the item name padded or cut on the left, the amount right-aligned at the end.

String line(String name, String amount, {int width = 32}) {
  final space = width - amount.length - 1;
  final left = name.length > space ? name.substring(0, space) : name.padRight(space);
  return '$left $amount\n';
}

The cedi sign

Receipt printers do not understand UTF-8. They print from a built-in code page, a table that maps each byte to one character, and the common code pages do not include ₵. Sending the three UTF-8 bytes for the cedi sign prints three unrelated characters instead. Writing amounts as GHS 24.00 avoids the problem. If the sign is essential, it has to be printed as a small image.

Bluetooth Classic or Bluetooth Low Energy

Check which kind of Bluetooth the printer uses before choosing a plugin. Many low-cost receipt printers use Bluetooth Classic with the Serial Port Profile, where the app opens a socket and writes bytes much as it would to a serial cable. Others use Bluetooth Low Energy (BLE), where data is written to a characteristic in small packets. Code written for one will not connect to the other.

Chunking for BLE

BLE limits how much can be written in a single packet. The limit comes from the MTU, which starts at 23 bytes, leaving 20 bytes for data, and can be raised by negotiation to as much as 517. Android apps can request a larger MTU; iOS negotiates it automatically. A whole receipt written in one call will fail or be cut short.

Sending the buffer in chunks no larger than the negotiated MTU minus three bytes of overhead, with a short pause between writes, also stops the printer's small input buffer from overflowing. With the flutter_blue_plus package it looks like this:

Future<void> sendInChunks(BluetoothCharacteristic printer, List<int> data, int mtu) async {
  final size = mtu - 3;
  for (var i = 0; i < data.length; i += size) {
    final end = i + size < data.length ? i + size : data.length;
    await printer.write(data.sublist(i, end), withoutResponse: true);
    await Future.delayed(const Duration(milliseconds: 10));
  }
}

The pause is a trade-off. Too short and some printers drop bytes, which shows up as missing letters or a receipt that stops halfway. Too long and printing feels slow. The right value depends on the printer, so it is worth making it a setting rather than a constant.

Test on the real printer

Cheap printers vary in which commands they support. Some ignore the cut command, some only do a full cut, some use different code pages. Before supporting a model, print a test receipt that uses every command the app sends, including the longest item name and the largest amount you expect, and check it on paper.
